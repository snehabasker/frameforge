# FrameForge

A small, distilled, temporally stable neural upscaler for real-time rendered frames (960x540 -> 1920x1080, x2), trained in PyTorch and shipped as a multithreaded C++ inference engine.

![bicubic vs FSR1 vs FrameForge vs ground truth](docs/comparison.gif)

Generated by `scripts/make_comparison_gif.py`, real ffmpeg output. **This is smoke-test-scale**: the sequence is the committed synthetic fixture (`tests/fixtures/`), not the project's real rendered dataset (which doesn't exist yet -- see [Limitations](#limitations-and-future-work)), and the FrameForge model shown was trained on this exact sequence (an overfit/plumbing check, not a generalization result). ## Key findings

- **The distillation pipeline runs correctly end to end**, verified at every boundary: PyTorch vs ONNX Runtime parity (max abs error <1e-4, all 4 model variants), and the C++ engine's full pipeline vs a live PyTorch reference on the same sequence (byte-level match). These are the numbers that matter most right now, because the model-quality numbers above are not yet at real scale.
- **The param budget holds with room to spare**: 119K/300K (40%) for the full temporal+depth variant, leaving headroom for a larger C/N if real-data results call for it.
- **Where the model loses (expected, not yet measured at scale)**: `scripts/extract_failure_crops.py` finds worst-error crops automatically, but the synthetic fixture has no disocclusions, thin geometry, fast motion, or specular highlights to characterize -- the categories CLAUDE.md asks about need the real rendered dataset (see Limitations). What IS known: the current motion-vector convention (`frameforge.data.exr_io.blender_vector_to_backward_flow`) is an documented, synthetic-data-verified *assumption* about Blender's real Vector pass, not yet empirically confirmed against a real render -- if wrong, temporal quality on real data would be the first place it shows up.
- **SpscRingBuffer beats BlockingQueue by 1.3x-8.6x** (depending on item count and metric) in real benchmarks on this machine -- the one profiling-driven optimization made for the engine, see `docs/RESULTS.md`.
- **Two verification gaps are open, not hidden**: ASan/UBSan/TSan are configured but unverifiable on this dev machine's MinGW toolchain (CI's Ubuntu jobs are the real check, not yet run); CPU flamegraphs need Linux `perf`, also unavailable here.

## Architecture

```
Python (train.py, export_onnx.py)              C++ (engine/)
─────────────────────────────────              ─────────────
FrameForgeNet (PyTorch)                         OrtModelRunner (ONNX Runtime C++)
  warp() inside forward()          --export-->    the SAME warp, as ONNX GridSample
  teacher distillation losses                    sequence_runner.cpp / pipeline.cpp
  recurrent unroll (run_unroll)                    recurrent inference loop
                                                   tile.cpp (tiled inference)
                                                   queue.hpp (2 queue implementations)
```

Full reasoning (recurrent-dependency constraints, concurrency model, queue benchmark, tiling, data flow, what's not built yet): [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## How to reproduce

```bash
# 1. Python environment
python -m venv .venv && .venv/Scripts/activate  # or .venv/bin/activate on Linux/macOS
pip install -e ".[dev]"

# 2. Run the test suite (uses committed synthetic fixtures, no external data needed)
pytest -q

# 3. Fetch pretrained weights + ONNX Runtime (SHA256-verified downloads)
python scripts/download_pretrained.py
python scripts/fetch_onnxruntime.py

# 4. Build the C++ engine (needs a C++17 compiler + CMake >= 3.20; see docs/DECISIONS.md
#    D1/D2 if you hit MinGW-specific issues on Windows)
cmake -S engine -B engine/build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build engine/build -j
ctest --test-dir engine/build --output-on-failure

# 5. Train (on the fixture, as a smoke test -- see docs/DECISIONS.md D0 for what a
#    real training run needs: a rendered dataset via blender/render_sequences.py,
#    which needs Blender, and a GPU session, e.g. Kaggle)
python -m frameforge.data.teacher_cache --root tests/fixtures/sequences \
    --out runs/teacher_cache --teacher-weights .weights_cache/swinir_classicalSR_x2.pth
python -m frameforge.train --train-config configs/train_C_output_feature_kd.yaml \
    --data-root tests/fixtures/sequences --teacher-cache-dir runs/teacher_cache

# 6. Export to ONNX and evaluate
python -m frameforge.export_onnx --checkpoint checkpoints/latest.pt --out export/model.onnx
python -m frameforge.evaluate --data-root tests/fixtures/sequences \
    --teacher-weights .weights_cache/swinir_classicalSR_x2.pth \
    --fsr1-cli engine/build/fsr1_easu/fsr1_cli \
    --student-checkpoints C=checkpoints/latest.pt --out results/metrics.csv
python scripts/gen_results_table.py --csv results/metrics.csv --out docs/RESULTS.md

# 7. Run the engine CLI on a sequence
engine/build/frameforge --model export/model.onnx --input <seq_dir> --output out/ --threads 4
```

One-command versions of steps 5-6 for the real dataset (once rendered) are the same commands with `--data-root` pointed at the real output of `blender/render_sequences.py`.

## Engine design summary

C++17, CMake, ONNX Runtime C++ API (CPU EP by default, CUDA EP behind `--ep cuda`), tinyexr + stb for I/O. The recurrent `O_{t-1} -> O_t` dependency means frames within one sequence infer strictly in order; concurrency instead comes from overlapping pipeline stages within a sequence and running independent sequences across a `--threads` worker pool. Two queue implementations (mutex+condvar `BlockingQueue`, lock-free `SpscRingBuffer`) are both benchmarked; the ring buffer is the default per real numbers, not assumption. Tiled inference blends overlapping tiles with linear feathering for inputs larger than memory allows. Full detail: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Limitations and future work

This codebase was built in an environment with **no Blender and no GPU-attached training session** (a Windows dev machine; see `docs/DECISIONS.md` D0 for the full reasoning). Every stage is real, tested, working code -- but two specific things are still pending real execution, not because they're unwritten, but because they need resources this environment didn't have:

1. **The real ~40-sequence rendered dataset.** `blender/render_sequences.py` and `configs/render.yaml` are written and syntax-checked but never run against real Blender scenes. Someone with Blender needs to pick CC0/CC-BY scenes (candidates noted in `configs/render.yaml`), fill in the scene list, and run the render.
2. **The real distillation training matrix (A/B/C/D) at scale**, on a GPU (e.g. Kaggle, per the project's zero-budget constraint). The full training/eval/results pipeline is verified correct on synthetic data (`docs/RESULTS.md`'s smoke-test numbers, all four experiment configs passing `test_train_integration.py`); it has not yet been run on real content.

Other open items, all documented in `docs/DECISIONS.md`:

- Blender's Vector-pass sign/axis/unit convention is an informed assumption (D4), verified against synthetic data, not yet against a real render.
- ASan/UBSan/TSan configured but unverifiable on this dev machine's MinGW toolchain (D8) -- CI is the real check.
- CPU flamegraphs need Linux `perf`, unavailable here (`scripts/flamegraph.sh` is written and documented, not run).
- Teacher-cache + on-the-fly cropping interact imperfectly (D6): the cache covers full-frame training; cropped training falls back to live teacher inference per-step, correctly but not as fast as intended.
