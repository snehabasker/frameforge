## C++ engine: queue benchmark and pipeline timing

**Hardware/software** (CLAUDE.md 7.5: "always record the hardware and software versions next to the numbers"): Intel Core i7-13620H (10 cores / 16 threads), Windows 11 Home 10.0.26200, GCC 16.2.0 (MinGW-w64/WinLibs, UCRT, POSIX threads), CMake 4.4.2, Ninja 1.13.2, ONNX Runtime 1.20.1 (CPU EP), Google Benchmark 1.9.1. Real run of `engine/build/bench/frameforge_bench.exe`, copied verbatim below (not retyped by hand):

```
Benchmark                              Time             CPU   Iterations UserCounters...
----------------------------------------------------------------------------------------
BM_BlockingQueue_SPSC/1000         0.706 ms        0.326 ms         1723 items_per_second=3.06311M/s
BM_BlockingQueue_SPSC/100000        67.3 ms         29.3 ms           24 items_per_second=3.41333M/s
BM_SpscRingBuffer_SPSC/1000        0.271 ms        0.246 ms         2036 items_per_second=4.072M/s
BM_SpscRingBuffer_SPSC/100000       8.13 ms         8.23 ms          112 items_per_second=12.1492M/s
```

`SpscRingBuffer` beats `BlockingQueue` by ~1.3x at 1,000 items and ~3.6x at 100,000 items (CPU time; wall-clock shows an even larger gap, ~8.3x, likely `BlockingQueue`'s condition-variable wakeups losing more to OS scheduling at high item counts). **This is the one profiling-driven optimization for M5**: the pipeline (`engine/src/pipeline.cpp`) defaults to `SpscRingBuffer` because of this measurement, per CLAUDE.md 7.3's "keep the better one as default" -- before benchmarking, `BlockingQueue` was the more obvious/simpler choice and would have shipped as the default without this data. `BlockingQueue` stays implemented and tested for the multi-producer/multi-consumer and `Close()`-shutdown cases `SpscRingBuffer` doesn't cover.

**Engine CLI, smoke-test scale**: `frameforge.exe` end to end (process start, ONNX session creation, EXR decode, tonemap, depth-normalize, inference, PNG write) on the 3-frame, 64x36->128x72 synthetic fixture sequence, three repeated runs: 140.8 ms, 130.4 ms, 129.7 ms total (~43-47 ms/frame, dominated by one-time ONNX session creation for such a tiny per-run frame count). **This is not a meaningful production latency number** -- the real target is 960x540->1920x1080 on the actual rendered dataset, which doesn't exist in this environment yet (docs/DECISIONS.md D0). Median/p95 ms/frame at 1 vs N threads and CPU vs CUDA EP, per CLAUDE.md 7.5, is a pending action item once real data and a GPU-enabled ONNX Runtime build are available.
